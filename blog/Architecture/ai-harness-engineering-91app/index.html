給 AI 蓋個工作環境：從 Harness Engineering 看 91APP 的 AI 輔助開發設計

你的 AI「熱心地」重構了不該動的核心架構——問題不是模型太聰明，是你沒設計它的工作環境。

為什麼 Coding Agent 越跑越歪？

GitHub Copilot 在工程師的鍵盤旁住了好幾年，但多數團隊用 AI 的方式，一年前跟現在沒有本質差異：貼程式碼、問問題、拿到建議再手動修。這個模式在「問答式」場景還勉強應付得來，一旦你把複雜任務丟給 Coding Agent，問題就會爆發。

三個讓 Agent 跑偏的根本原因

  • 隱性知識消失是主因：有經驗的工程師靠「直覺和潛規則」填補需求文件到實作之間的落差——這個 method 不能動、這個命名是全組的慣例、這個模組的邊界不能跨越。這些知識只活在人的腦子裡。AI 接手後全蒸發了，它只能靠文字描述工作，結果熱心地把架構改得面目全非。

  • 給的 context 決定 AI 輸出精準度：把 AI 開發的 context 品質分成四個層次：只給 User Story（L1）幻覺率最高；加上技術規格 Arc42（L2）讓 AI 理解結構；加上參考程式碼（L3）讓 AI 模仿風格；完整提供 API 與 Job 架構圖（L4）才能達到足夠的精準。但多數團隊停留在 L1，然後抱怨 AI 不好用。

  • 長任務的錯誤代價比你想的高：問答式場景下 AI 偏了，你立刻發現、立刻修，損失有限。但 Coding Agent 可能跑了一個小時才產出 PR，如果從第一步方向就錯了，代價極高。這不是模型問題，是沒有系統性地設計 AI 的工作環境。

你可能會想：給更好的 prompt 不就解決了嗎？

Prompt 是一次性的，只影響這一次對話。今天把規範寫進 prompt，明天換個工程師、換個任務，這些規範消失了。真正的解法是把規範、架構知識、慣例永久放進 AI 的工作環境裡，不靠每次重新提醒。這就是 Context Engineering 的核心，也是 Harness 設計要解決的問題。

Harness：給 AI 設計一個工作環境

Martin Fowler 在《Harness Engineering for Coding Agent Users》裡提出了一個公式：Agent = Model + Harness。Model 是你租來的大腦，Harness 是你為這個大腦設計的整個工作環境。說白了，多數人把精力花在挑模型，卻忽略了工作環境的設計。

Feedforward（事前引導）和 Feedback Sensor（事後偵測）缺一不可

  • Feedforward（事前引導）提高第一次就做對的機率：在 AI 動工「之前」注入引導——coding 規範、架構邊界的說明、不能做的事情清單。這些引導像路邊的護欄，在 AI 還沒犯錯之前就把它引導到對的方向。

  • Feedback Sensor（事後偵測機制）建立自我修正的迴圈：在 AI 動工「之後」觀察並給出訊號，例如 linter、型別檢查、AI code review。關鍵在於 Sensor 的訊息要讓 AI 看得懂並知道怎麼修——不只報錯，要告訴它「怎麼修正」。

  • 兩者缺一不可，而且越早偵測越好：只有事前引導，你永遠不知道規範有沒有被執行到；只有事後偵測，AI 從第一步就走偏，後面修正成本很高。在 commit 前抓到的問題，比在 PR review 才發現便宜太多了。

  • 兩種偵測工具各有適用場景：自動執行的確定性工具（linter、型別檢查、架構測試）速度快、結果明確，是基礎層；AI code review 這類語意層判斷速度慢、結果不確定，但補足了自動工具看不到的地方。兩種都需要，不能互相取代。

讓 Sensor 說「人話」：好的錯誤訊息應該告訴 AI 怎麼修

Sensor 的訊息要「LLM 友善」——不只報錯，還要告訴 AI 如何修正，才能驅動自動修正迴圈：

❌ 不好的 Sensor 輸出： Error: module boundary violated at UserService.cs:42

✅ 好的 Sensor 輸出： UserService 引用了 OrderModule，違反 Bounded Context 規則。建議把共用邏輯移到 SharedKernel，或加一層 Anti-Corruption Layer。參見：docs/architecture/module-boundaries.md

前者讓 AI 不知所措；後者直接告訴 AI 下一步怎麼做，這是讓 Agent 能自我修正的關鍵設計。

91APP 的實作：三道關卡 + 兩層防護

把品質問題推到最前面解決，而不是出錯後補救

我們在 AI 輔助開發的設計核心是：靠 instructions、Skills、Agents 做大量的事前引導，用 Build/Test Gate 守底線，並在 Coding Agent 動工之前設三道審查關卡。這是「Keep Quality Left（品質左移）」的詮釋——不是把 Sensor 塞進 commit hook，而是在需求階段就消除不確定性。

Clarify → Plan → Tasks：讓 Coding Agent 收到的永遠是已驗證的規格

  • Clarify（需求審查關卡）：掃描需求模糊點，同時做技術相容性檢查——版本升級、新整合、破壞性變更自動觸發掃描，在架構決策之前就攔截潛在問題。

  • Plan（架構設計關卡）：做 Arc42 架構設計，把 Implement Plan 寫回 Azure DevOps，讓架構決策有明確的書面記錄，而不是工程師腦袋裡的口頭共識。

  • Tasks（任務拆解關卡）：把 Plan 拆解成原子化任務，通過六維品質檢查（邊界清晰、平行安全、可驗證、可回滾……），確保每個任務都能獨立執行、不互相干擾。

Clarify（掃描需求模糊點 + 技術相容性檢查）
  → Plan（Arc42 架構設計 + Implement Plan 寫回 Azure DevOps）
    → Tasks（原子化拆解 + 平行邊界分析）
      → Coding Agent（已被三輪驗證的規格）

  • Progressive Disclosure（漸進揭露）解決 context window 上限：SKILL.md 本體極簡（Quick Start 5 步），詳細說明藏在 references/ 子目錄按需載入。這不只是文件組織方式，而是工程限制的解法——Harness 設計再完整，也不能把整個規範一次塞進 context window。

  • Azure DevOps 作為唯一的事實來源：所有偵測機制（code review、user story compliance checker）的判斷基準，都指向 Azure DevOps Work Item 的 Description 和 Implement Plan，而不是散落的 README 或口頭共識。讓 AI 判斷 [BLOCKED] 時有明確依據，不需要靠猜。

三道關卡感覺感覺很繁瑣，能不能跳過一些步驟？

三道關卡是為了消除不同層次的不確定性。Clarify 消除「需求理解的模糊」，Plan 消除「架構決策的不確定」，Tasks 消除「實作範圍的邊界不清」。跳過哪一步，就是把那層的不確定性留給 Coding Agent 自己猜。簡單任務可以跳，複雜任務跳了代價很高。AI Code Review 的兩層設計（Computational 守基礎 + Inferential 補語意）也是同樣邏輯：前者便宜可靠，後者補足盲區，缺一都有風險。

Context 品質：決定你能從 AI 輔助開發拿到多少生產力

從「寫程式的人」，變成「設計 AI 工作環境的人」

「停止工程化 Prompt，改工程化 Context」——這句話說的是工程師角色的根本轉移：從親自寫每一行程式，變成 Context Architect（負責設計 AI 工作信息環境的人）。你設計的不是 prompt，而是 AI 每次執行時周圍永久存在的信息環境，例如：instructions.md、Implement Plan、Arc42 架構文件、constitution.md 等等。

給的資訊不在夠多，在夠準！

  • 讓 Coding Agent 進入有足夠 context 的環境：Clarify 填入技術規格（Arc42），Plan 填入架構決策（ImplementPlan），Tasks 填入任務邊界，讓 Coding Agent 收到任務時已有完整的 API/Job 架構脈絡。

  • 高風險模組和標準化任務，適合不同的工作模式：核心業務邏輯的探索性修改（外科醫生模式）適合人持續監督、AI 作副駕；CRUD、測試生成、文件產出這類標準化工作（裝配線模式）適合 Coding Agent 自動執行、人只做確認。這個分工讓你的注意力放在 AI 真的需要你盯著的地方。

  • Commander of Agents 模式：一人管多個 Agent 並行：當三道關卡的規格品質夠高，一位工程師可以同時管理 3–5 個 Cloud Agent，每個處理不同功能模組，在背景自動建 branch、建 PR。生產力提升的來源不是 AI 跑得更快，而是你的等待時間被消除了。

  • Context Engineering 和 Prompt Engineering 是兩個層次的事：Prompt Engineering 關注「這次對話要怎麼問」，效果隨對話結束消失。Context Engineering 關注「AI 的工作環境裡永久存在什麼」，效果累積、不依賴每次重新提醒。前者是技巧，後者是系統設計。

目前還差什麼：已知空缺和下一步建議

Harness 是累積型投資，但哪裡有洞得先看清楚

91APP 的設計有清楚的優先序，但也有幾個已知的空缺。這不是缺陷，而是還沒投資的地方。好的 Harness 設計不需要一次到位，而是每次 AI 犯了重複性錯誤，就補上對應的防護機制。

四個有明確改善空間的地方

  • 架構邊界沒有自動化偵測：只用文字說明邊界（靠 AI 讀懂遵守），沒有自動執行的架構測試（例如： ArchUnit 或 dep-cruiser）。架構邊界被違反時，只能靠 AI code review 發現，不是確定性地攔截。系統越大，這個洞越危險。

  • Sensor 輸出格式還沒標準化：Dify Stage 2 的語意層 code review 方向是對的，但輸出格式依賴 prompt 品質，沒有標準化成「告訴 AI 怎麼修正」的固定格式。Sensor 輸出不穩定，Stage 4 的自動修正迴圈效果就會搖擺。

  • 測試有沒有保護力，目前看不出來：Quality Gate 確保測試「跑得過」，但無法驗證測試是否真的能抓到 bug。Mutation Testing（故意插入小錯誤、看測試有沒有抓到）是補足這個空缺的工具，對 Coding Agent 生成的測試特別有意義。

  • 功能對不對，目前還靠人工驗：只有 Unit Test，功能正確性的最終確認仍依賴人工 QA。E2E 自動測試 + LLM 作為評分者是目前最接近「讓 AI 自己驗功能正確性」的組合，但業界還沒有成熟解法。

有限資源先補哪個？

依「同樣錯誤重複發生的頻率」決定優先序：

  1. Sensor 輸出格式標準化：成本最低、效益最直接，改善現有自動修正迴圈的成功率。建議優先。
  2. 架構邊界自動化測試：系統複雜度提高後靠文字說明約束邊界越來越不可靠，ArchUnit 或 dep-cruiser 引入成本不高，但預防的架構漂移問題代價很高。
  3. Mutation Testing：等 Cloud Agent 任務量提高後再評估，目前優先序較低。

結論

Harness Engineering 說的不是工具清單，而是一種思維轉移：從「我要怎麼跟 AI 說話」，變成「我要為 AI 設計什麼樣的工作環境」。

91APP 的三道審查關卡（Clarify→Plan→Tasks）、漸進揭露的 SKILL 結構、Azure DevOps 作為唯一事實來源——這些設計讓 Coding Agent 收到任務時已處於好的 context 環境，是 Commander of Agents 模式能成立的工程基礎。

AI 輔助開發的下一步不是換更強的模型，而是持續校正（steering）：每次需要人工介入的地方，就是工作環境還有洞的地方——補上它，讓AI 下次做的時候自己就能處理好。
