當 AI 變成你的 QA：91APP 如何打造一套自動執行 Test Case 的系統

Roland Chao2026/05/08

傳統的自動化測試有一個讓人又愛又恨的特質：寫起來費時、壞起來超快。每次前端改版，Locator 失效、腳本報錯，維護成本比重新手動測試還高。91APP 決定換一個思路：讓 AI 來執行測試，而不只是「讓工具替代人工點擊」。

這篇文章分享 91APP 建置的 AI 驅動自動化測試系統，從整體架構、Playwright-skill 框架設計，到 AI 決策流程與 Skill 開發工作流，帶你了解這套系統是如何運作的。

為什麼需要重新設計自動化測試

傳統自動化的瓶頸不只是「速度」

自動化測試在理想上是「寫一次，跑百次」，但在實際產品開發中往往走樣。UI 改版後 Selector 失效、測試資料難以管理、腳本邏輯和業務邏輯脫鉤。更根本的問題是，寫自動化腳本的人需要同時懂測試邏輯與前端 HTML 結構，這個技能門檻讓 QA 和開發之間一直有道鴻溝。

另一個痛點是測試的「觸發時機」。手動測試通常等到 Sprint 末期才集中跑，即使有自動化腳本，也往往要等 QA 手動觸發。如果能在 QA 建立 test case 後立刻自動執行，整個回饋迴圈就會快很多。

AI 輔助開發如何改變 QA 的工作方式

91APP 的做法是：QA 負責描述測試情境（Given-When-Then），AI 負責執行。這不是說 QA 不需要懂測試，而是把 QA 的價值集中在「設計好的測試情境」上，而不是「寫腳本和維護 Selector」。

流程起點是透過 AI 工具（例如：GitHub Copilot CLI）產出結構化的 test case，包含前置條件（Given）、執行步驟（When）、預期結果（Then），並標記哪些案例可以自動化執行（自動化測試: True）。一旦 QA 在 Azure DevOps task 上打上 auto-test 標籤，整套自動化系統就自動接手。

從 Webhook 到測試完成：系統架構全貌

三層架構：觸發 → 調度 → 回報

（圖：作者自製）

整個系統架構可以分為三個層次：

一、觸發入口（Trigger Entry） 有兩種：

  1. Azure DevOps Service Hook：work item 建立或更新、帶有 auto-test 標籤（且尚無 auto-test-dispatched 或 auto-test-completed）時，WebAPI 接收 Webhook、驗證標籤後送入 SQS Queue。
  2. Cron Job：定期掃描符合條件的任務，補抓可能因時序問題遺漏的 work item，確保沒有任務被跳過。

二、調度層（SQS Queue + Workers） 以 AWS SQS 作為核心訊息佇列。Worker 以 Long Polling 批次模式監聽，支援 Concurrency Control，可水平擴展多個 Worker 同時執行不同任務，互不干擾。

三、回報層（Reporting） 測試完成後透過三個管道回報：

  • Azure DevOps（加 Comment + Completion Tag）
  • Slack（發送結果通知）
  • SQS（deleteMessage() 清除已處理的訊息）

Worker 的初始化與主迴圈

Worker 啟動時先進行一次性初始化，完成環境準備（Git 設定、套件認證、Clone 所需 Repository、初始化執行環境），並預先準備好隔離的執行 Slot。初始化完成後進入主迴圈：持續以批次方式監聽訊息佇列、並行控制多個任務同時執行，互不干擾。

每筆訊息對應一個測試任務，Worker 鎖定任務後解析測試目標與計畫資訊，再交由 AI Agent Runner 驅動 AI 執行對應的 Playwright-skill，並解析回傳的執行結果。

三層結果判斷：不只是 Pass/Fail

執行完成後，系統以三層邏輯判斷：

  1. Query Test Point outcome：從 test case 執行結果取得狀態（最多等待 5 秒）
  2. Parse latest comment：解析最新留言中的 [TEST_RESULT:PASS] 或 [TEST_RESULT:FAIL] 標記
  3. null：代表該 case 尚未被測試

三層判斷讓系統能處理 AI 執行後「結果尚未寫入」的短暫延遲，也能識別「執行了但沒有任何結論」的狀態。

Playwright-skill 框架：把頁面知識封裝起來

為什麼不讓 AI 直接操作 Playwright

這是整套系統最核心的設計決策。如果讓 AI 每次從頭用 Playwright CLI 探索 HTML 結構、猜測 Selector，穩定性和效率都會很差。Playwright-skill 框架的設計哲學是：把頁面知識封裝成可複用的 Skill，讓 AI 呼叫高層次的操作，而不是底層的點擊指令。

Skill.md 與 Reference.md：讓 AI 知道邊界在哪

每個 Skill 目錄帶有兩個文件：

  • SKILL.md：定義前置條件（瀏覽器需已啟動、CDP 連線狀態、shop_id 是否有效）、可用腳本清單、必填參數，以及各種失敗情境的處理指引。AI 收到任務時會先讀這份文件確認前置條件。
  • REFERENCE.md：更詳細的使用說明，包含每個 Page Object 支援的 action 完整列表，讓 AI 知道在這個頁面上「可以做什麼、不能猜什麼」。

為什麼需要 SKILL.md？直接讓 AI 探索不行嗎？

沒有邊界文件的 AI 很容易「自由發揮」——猜測 URL 路徑、自己寫 Python 腳本繞過 Skill、或在應該立即停止的情況下繼續重試。SKILL.md 明確列出「絕對禁止事項」，讓 AI 執行行為可預期，QE 可以從 agent.log 驗證 AI 是否確實遵循了流程。

讓 AI 自己建立新的 Skill

從說需求到 Skill 就緒

當 QA 需要新增尚未有 Skill 的頁面，只需提供頁面名稱、URL 與所需的操作描述，其餘由 AI 依照標準化開發流程自動完成：啟動瀏覽器連線探索頁面結構、生成並驗證 Locator、開發 Action 方法，最後自動更新 Skill 文件並歸檔。

其中一個關鍵品質關卡是「AI 自驗」：在歸檔前，AI 會對每個 Action 進行冒煙測試，確認基本可用性；若失敗則自行修復後重跑（最多三次），確保新 Skill 在交給 QA 執行正式 test case 之前已通過基本驗證。整個開發過程中，QA 只需在最初提供需求描述，其餘全由 AI 自行完成。

結論

91APP 這套系統的核心洞察是：自動化測試最大的成本不是「執行」，而是「維護」與「知識轉移」。透過把頁面知識封裝進 Playwright-skill 框架、讓 AI Agent 依照結構化 Skill 執行，而不是每次從頭探索 HTML，系統在穩定性和可維護性上都有明顯改善。

從 QA 的角度來看，工作重心從「寫腳本和修 Selector」轉移到「設計好的 Given-When-Then 情境」，這是更有價值的地方。從開發端來看，新增一個頁面的 Skill 只需告訴 AI 需求，其餘由 AI 自己完成。

這套架構並非一步到位，而是從 Page Object 設計規範、Skill 文件標準，到三層決策模型的逐步演化，每一個設計決策都有其背後遇到的實際問題。如果你正在思考如何讓 AI 真正進入你的測試流程，這套架構是一個值得參考的起點。
