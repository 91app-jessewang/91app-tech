91APP 用 AI 打通從需求到自動化測試的整條路

Mia Chen2026/05/15

從 PRD 到 Test Case——QA 為什麼需要一條系統化的路

傳統 QA 流程藏著哪些隱藏成本？

每個 QA 工程師都熟悉這個場景：拿到一份 User Story，讀完 AC（Acceptance Criteria），然後開始憑經驗和直覺撰寫測試案例。這個過程沒有標準，測試粒度全靠個人功力，測試資料更是一筆一筆手動整理。在大型專案中，這種方式有一個致命問題——你很容易「見樹不見林」，專注在單一 Story 的細節，卻漏掉跨模組的整合風險。

更棘手的是，當測試案例要接 Playwright 自動化時，「填帳號密碼後點登入」這種描述根本不夠精確。Playwright 需要知道每一個 DOM 互動、每一個 assert 的具體語意，手寫的案例幾乎都需要大幅度重寫才能執行。

91APP 為此提出了 AI-Driven Development for QA 的解法：以 AI 串接六個自動化步驟，從產品需求文件（PRD）一路走到可執行的 Playwright UI 測試案例，並整合 Azure DevOps 進行全程任務追蹤。

設計哲學：AI 承擔結構化工作，人聚焦判斷

我們的核心思想不是「讓 AI 取代 QA」，而是「讓 AI 承擔結構化、可規則化的工作，讓 QA 聚焦在判斷和審查」。整個流程分為三個階段：

  • 規劃階段：從 PRD 生成 Q42 品質文件與 TestPlan，建立 Azure DevOps QA Task
  • 開發階段：從 Story 生成 Test Goal → 測試資料 → UI TestCase，推送至 Azure Test Plans
  • 驗證階段：執行自動化測試，根據結果更新 Task 狀態

整個泳道圖（swim lane diagram）清楚切分了「AI 自動執行」和「人工審查」的邊界——黃色節點是 AI Prompt 驅動，綠色節點是自動化，人只需要在幾個關鍵決策點介入。

整條流程的快速全景

六個核心步驟環環相扣，每個步驟的輸出即為下一步的輸入：

  1. 建立 QA Task
  2. 生成 Test Goal
  3. 準備測試資料清單
  4. 產生 UI Test Case
  5. 推送至 Azure Test Plans
  6. 更新 Test Goal List

Q42——把模糊需求變成品質目標的第一步

為什麼叫 Q42？ 架構師有 arc42 作為系統架構的標準文件框架，QA 當然也要有自己的 42。Q 代表 Quality，42 代表⋯⋯宇宙萬物的終極答案——也是「我們到底要測什麼？」這個問題在 Sprint 開始前就應該有的終極回應。

為什麼大型專案需要在 Sprint 前定義品質策略？

在沒有 Q42 的環境下，每個 Story 的 QA 只看自己那一塊，跨 Sprint 的整合測試很容易被忽略。而且，測試範疇和測試資源的分配往往到 Sprint 末期才開始討論，這時再調整已經太晚了。

Q42 是 91APP 為大型專案設計的「品質控管中心」，在 Sprint 開始之前就定義清楚「測什麼」和「怎麼測」，讓後續的 Test Goal 生成有清楚的策略依據，而不是每次都從零開始推斷。

三份文件組成完整的品質追溯鏈

Q42 由三份核心文件組成，各自回答不同層次的問題：

  • Quality Requirements（QR）：定義「為什麼測」與「測什麼」——從商業目標出發，列出哪些功能必須達到什麼品質標準
  • Quality Verification（QV）：定義「怎麼測」與「資源分配」——列出測試環境、裝置需求、跨市場適用性等具體約束，以及各 Sprint 的測試重點與 QA 提醒
  • GSO 追溯鏈：建立 Goal（目標）→ Scenario（情境）→ Objective（重點）的三層結構，確保每條測項都有商業價值與品質依據可追溯

三份文件都由 AI 協助從 PRD 自動生成，並由品質管理員進行人工審查後確認。

Sprint 銜接模式：解決「見樹不見林」

對大型專案，我們提供了「Sprint 銜接模式」：在生成每個 Story 的 Test Goal 時，AI 不只讀取當前 Story，還會「向上追溯」讀取 QV 文件的 Sprint 測試計畫，自動提取該 Sprint 的「測試重點」與「QA 提醒」，結合全域策略與局部細節，產出符合專案標準的測試情境。

這個設計的價值在於：QA 不需要反覆確認「這個 Story 有沒有影響到上個 Sprint 的功能」，AI 會在生成 Test Goal 時就把跨 Sprint 的風險帶入。

沒有 PRD 文件的小型專案怎麼辦？

可直接從 Story 描述和 AC 生成 Test Goal，然後生成 UI Test Cases。

六大步驟解析

六個步驟形成一條完整的生產線，每個步驟的輸出都是下一步的輸入。

步驟一到三：從需求到測試計畫

目的是把模糊的需求文件轉換成結構化的測試規劃：

  • Step 1：在 Azure DevOps 建立 QA 追蹤任務，讓測試工作有看板節點
  • Step 2：核心步驟，AI 依 ISO 29119-3 標準拆分測試目標與情境，產出各優先級的測項清單
  • Step 3：生成測試資料清單

步驟四到六：從測試計畫到可執行自動化

目的是把測試計畫轉換成可以實際執行的自動化測試，並同步回追蹤系統：

  • Step 4：產生嚴格規範的 UI Test Case（Given/When/Then 結構），讓 Playwright 可以直接執行
  • Step 5：推送至 Azure Test Plans，並把 UI Steps 寫入對應欄位，觸發遠端自動化 Job
  • Step 6：更新 Test Goal List，讓整條追蹤鏈路完整閉環

UI Test Case 生成規範——讓每個步驟都可自動執行

為什麼 AI 生成的 Test Case 不能直接跑？

大多數 AI 工具生成的測試步驟都有一個共同問題：步驟描述模糊（「填寫帳號密碼後點登入」），或者 Then 的斷言不具體（「應該顯示正確結果」）。這樣的 Test Case 人工執行沒問題，但 Playwright 根本不知道要 assert 什麼。

我們透過三層規範讓生成的每個步驟都精確到可以直接執行。

一、Given / When / Then 的嚴格化規範

Given（前置條件）：

  • 禁止交叉參照（不能寫「同 XX-01 流程」，必須完整展開）
  • 後端不可見狀態一律省略（DB flag、內部設定不可見就不寫）
  • 「確認」步驟須描述具體 UI 狀態，而非描述意圖

When（操作步驟）：

  • 一步驟 = 一個 DOM 互動，不允許合併動作
  • 動詞限定 7 個：點擊 / 輸入 / 選擇 / 勾選 / 滑動 / 等待 / 前往
  • ❌「填帳號密碼後點登入」→ ✅ 拆分為 W1: "帳號" 輸入 "demo_user_a"、W2: "密碼" 輸入 "●●●●●●"、W3: 點擊 "登入" 按鈕

Then（預期結果）：

  • 禁止模糊詞：應該、正確、正常、符合預期
  • 須對應 Playwright 斷言語意：toHaveText / toBeVisible / toBeChecked

二、Skill Labels 讓步驟自動對應到 Playwright 實作

撰寫步驟前必須載入 Playwright Skill 標籤索引。有對應 Action 的步驟套上 [Skill: xxx] 標籤，讓 Playwright Skill 可以自動執行；無對應的步驟改用自然語言描述，等待後續補充 Skill 實作。

以下是一個實際的 UI Test Case 輸出片段：

## Given:
| 步驟 | 描述 |
|------|------|
| G1.  | [Skill: web.login_page.login_with_web_api] ShopID: DEMO-001，帳號 F (demo_user_a / ●●●●●●) |
| G2.  | 確認登入成功（頁面右上角顯示會員圖示）|
| G3.  | [Skill: web.sale_page.goto_sale_page] 前往 DEMO-PROD-001 預約商品B 商品頁 |
| G4.  | [Skill: web.sale_page.click_add_to_cart] 加入預約車（門市預約商品，點擊自動加入）|

## When:
| 步驟 | 描述 |
|------|------|
| W1.  | [Skill: web.common_page.go_to_shopping_cart_page] 前往 ShopID: DEMO-001 購物車頁面 |
| W2.  | 等待購物車頁面載入完成（商品列表可見）|

## Then:
| 步驟 | 預期結果 |
|------|---------|
| T1.  | 預約車提示 BAR 顯示於頁面最上方（元素可見）|
| T2.  | 超過結帳金額上限提示 BAR 顯示於預約車提示 BAR 之後（第二位）|
| T3.  | 兩個 BAR 同時顯示，互不覆蓋（兩者均可見）|

## Teardown:
| 步驟 | 描述 |
|------|------|
| TD1. | [Skill: web.api.clear_cart] 清空購物車 |

三、16 條自我審查 Checklist 確保品質閘

AI 在產出 Test Case 後自動執行 16 條品質檢查，關鍵項目包括：

  • When 每步驟只有一個 DOM 互動？
  • When 步驟以限定動詞開頭？
  • Then 不含「應該」「正確」「正常」等模糊詞？
  • Given 無交叉參照、無後端不可見狀態？
  • 所有步驟已比對 Skill 標籤清單？

有問題直接修正，不等人工確認。

整合 Azure DevOps——讓測試追蹤完整閉環

沒有閉環，測試管理就是記帳不是管理

沒有閉環的測試管理，最終的結果就是：測試案例在文件裡，執行結果在 chat 裡，Task 狀態永遠是手動更新的猜測值。任何想查「這個 Story 的自動化覆蓋率」的人都必須手動翻文件，而文件是否即時更新完全取決於個人習慣。

我們透過 Step 5 推送至 Azure Test Plans 和 Step 6 更新 Test Goal List 把這條鏈路接起來。

從 Test Goal 到 Azure Test Plans 的完整同步

Step 5 執行後：

  • Azure Test Plans 自動建立對應的 Test Cases，每個 Test Goal 條目都有獨立的 Test Case ID
  • UI Test Case 的詳細步驟（Given/When/Then）寫入 Test Case 的自訂欄位「UI Steps」
  • 遠端自動化 Job 讀取 UI Steps 後，直接執行對應的 Playwright 測試，不需要手動觸發

Step 6 執行後：

  • 測項清單（包含 Test Case ID、測試情境標題、是否自動化）自動寫入 Azure Task 的「Test Goal List」欄位
  • Task 的狀態在測試完成後更新為 Done，完成從 New 到 Done 的完整生命週期

以一個實際的 Story 為例，一次性建立了 22 個 Test Cases（HP: 2 項、P0: 8 項、P2: 9 項、P3: 3 項），每個 Test Case 都有明確的自動化標記（True/False）。這讓 QA Lead 可以在任何時間點直接從 Azure DevOps 掌握自動化覆蓋率，而不需要再問人。

沒有 Playwright Skill 實作的步驟會怎樣？

步驟仍然會被寫入 UI Steps，但不帶 [Skill: xxx] 標籤。自動化 Job 遇到沒有標籤的步驟會跳過，等待工程師補充對應的 Skill 實作後再執行。這讓部分自動化優先落地，而不是等到 100% 再開始。

結論

這套流程的設計哲學不是用 AI 取代 QA，而是把「結構化但繁瑣」的工作交給 AI，讓 QA 工程師的精力集中在真正需要人類判斷的地方：測試策略制定、測試資料的合理性驗證、以及邊界情境的識別。

六大步驟的核心價值在於「有規則、可追蹤、可執行」三個特質。Test Goal 遵循 ISO 29119-3 標準確保測試覆蓋完整；UI Test Case 的嚴格規範確保每個步驟都可以對應到 Playwright 斷言；Azure DevOps 的整合確保每個測項的生命週期都有清楚的追蹤記錄。

對想要落地 AI 開發的團隊，建議從 Step 2（Test Goal 生成）開始試行，先感受 AI 如何根據 User Story 產出測試情境，驗證品質後再逐步接上 Step 4（UI Test Case 生成）和 Step 5（推送 Azure Test Plans）。完整閉環的建立需要時間，但每接上一個步驟，QA 流程的可預期性就會提升一個層次。
